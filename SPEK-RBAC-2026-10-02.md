# Spesifikasi RBAC ERP Azhan — Lapisan 1 Roadmap

Tanggal: 2 Oktober 2026 · Status: disetujui (Opsi B — role & permission sebagai data)
Acuan: dokumen "Arsitektur Terintegrasi Azhan Grup" + `modul.md` (Drive IT/)

## 1. Tujuan & prinsip

- Mengganti `admin_users.role ENUM('admin','cs')` dengan role & permission **sebagai data**, tanpa big-bang.
- Role menjawab "siapa boleh apa"; tim/divisi (modul pegawai, menyusul di Marketing Hub) menjawab "siapa mengerjakan apa" — keduanya dipisah.
- Scope data **tidak** masuk string permission: tetap lewat `brand_id` (NULL = grup) di middleware/repository, pola yang sudah berjalan.
- ERP = IdP grup: provisioning/deactivation akun CRM hanya dari ERP (`/api/admin/crm/users`); offboarding satu aksi.
- Allowlist CRM (`RequireAdminOrCRMAccess`, [middleware.go:57](internal/identity/middleware.go:57)) **dipertahankan apa adanya** — itu boundary antar sistem, bukan RBAC.

## 2. Skema database (migrasi `071_rbac.sql`)

```sql
CREATE TABLE roles (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  slug VARCHAR(64) UNIQUE NOT NULL,          -- 'super_admin_grup', 'cs', ...
  name VARCHAR(128) NOT NULL,                -- label tampilan
  is_system BOOLEAN NOT NULL DEFAULT FALSE,  -- role seed: tidak bisa dihapus dari UI
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB;

CREATE TABLE permissions (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  code VARCHAR(96) UNIQUE NOT NULL,          -- 'booking.view', 'payment.verify', ...
  description VARCHAR(255) NOT NULL
) ENGINE=InnoDB;

CREATE TABLE role_permissions (
  role_id BIGINT UNSIGNED NOT NULL,
  permission_id BIGINT UNSIGNED NOT NULL,
  PRIMARY KEY (role_id, permission_id),
  FOREIGN KEY (role_id) REFERENCES roles(id) ON DELETE CASCADE,
  FOREIGN KEY (permission_id) REFERENCES permissions(id) ON DELETE CASCADE
) ENGINE=InnoDB;

CREATE TABLE user_roles (
  admin_user_id BIGINT UNSIGNED NOT NULL,
  role_id BIGINT UNSIGNED NOT NULL,
  PRIMARY KEY (admin_user_id, role_id),
  FOREIGN KEY (admin_user_id) REFERENCES admin_users(id) ON DELETE CASCADE,
  FOREIGN KEY (role_id) REFERENCES roles(id) ON DELETE CASCADE
) ENGINE=InnoDB;

-- paksa re-login/refresh saat role user berubah
ALTER TABLE admin_users ADD COLUMN perm_version INT NOT NULL DEFAULT 0;
```

Catatan:
- Satu user boleh multi-role (kasus nyata: CMO merangkap IT).
- `admin_users.role` ENUM **tidak dihapus dulu** (fase 3) — dipakai fallback selama transisi.
- Scope cabang (`cabang_id`) belum dibuat; kolom ditambah saat modul cabang dikerjakan — desain tidak menghalangi.

## 5. JWT & identity

Claims access token ([jwt.go:50](internal/identity/jwt.go:50)) ditambah:

```
"roles": ["admin_travel"],          // slug, untuk tampilan/debug
"perms": ["booking.view", ...],     // dipakai middleware, tanpa query DB per request
"pver":  3                          // perm_version user saat token dibuat
```

- `brand_id`, `role` (lama) **tetap dikirim** selama transisi — handler lama tidak pecah.
- Perubahan role/permission user → `perm_version++` + revoke refresh token (tabel migrasi 059) → user refresh/login ulang mendapat perms baru. Middleware menolak token yang `pver` ≠ `perm_version` DB? **Tidak** — cukup andalkan TTL access token pendek + revoke refresh; hindari query DB per request. (Keputusan sadar: jendela maksimal = sisa umur access token.)
- Estimasi ukuran: ±50 perms ≈ 1–1,5 KB claim — aman untuk header.

## 6. Middleware

```go
// internal/identity/rbac.go
func RequirePermission(perm string) func(http.Handler) http.Handler
// baca perms dari context (diisi RequireAuth dari claim), 403 jika tidak ada.
```

- `RequireAdminRole` → wrapper: lolos jika punya permission apa pun selain milik `cs` (transisi), lalu per-route diganti `RequirePermission` bertahap.
- `brand.RequireSuperAdmin` → `RequirePermission("user.admin")` / permission spesifik per kasus; konvensi `brand_id NULL = grup` tetap untuk scoping data.
- `RequireAdminOrCRMAccess` tidak berubah.

## 7. Endpoint & UI manajemen

- `GET/POST/PUT /api/admin/roles`, `GET /api/admin/permissions`, `PUT /api/admin/users/{id}/roles` — semua di balik `user.admin`.
- Master-dashboard `UserManagementPage` diperluas: assign multi-role per user; matriks role×permission **read-only di UI** untuk role `is_system` (ubah lewat seed/migrasi supaya ter-review di git).
- Audit: setiap perubahan role/permission dicatat (tabel `audit_log` generik menyusul di approval engine; sementara cukup log aplikasi terstruktur).

## 8. Urutan implementasi (3 fase, tiap fase deploy-able)

1. **Fase 1 — fondasi (tanpa perubahan perilaku):** migrasi 071 + seed + pemetaan akun lama; JWT ditambah `roles/perms/pver`; `RequirePermission` tersedia; endpoint role management + UI. Semua route lama masih pakai middleware lama.
2. **Fase 2 — alih route bertahap:** ganti guard per kelompok modul (urutan: payment/refund → booking/jamaah → paket/master → agen → analytics), satu PR per kelompok, uji per kelompok. `RequireAdminRole` menyusut jadi tidak terpakai.
3. **Fase 3 — bersih-bersih:** hapus fallback `role` ENUM dari logika (kolom boleh tinggal untuk arsip), hapus wrapper lama, tulis dokumentasi role di README.
